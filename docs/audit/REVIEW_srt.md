# src-tauri/src/srt.rs 深度审查报告

## 1) 问题列表（含行号与严重度）

1. **[HIGH] 行 24-35：`needs_distribute` 一旦命中任意异常片段，会覆写所有片段时间戳**  
   - 现状：`any(|e <= s|)` 为真时，整个 `fixed` 被等分重写。  
   - 风险：只要一个片段坏数据，其他原本有效时间戳也被破坏，导致字幕整体与语音错位。

2. **[HIGH] 行 24、42：未把 `NaN/Inf` 作为“无效时间戳”参与修复，导致静默错误输出**  
   - 现状：`NaN` 比较结果为 false，可能使 `needs_distribute` 误判为 false；随后 `format_ts` 将 `NaN/负值` 直接变成 `00:00:00,000`。  
   - 风险：生成的 SRT 看似成功，实际时间轴错误且难排查。

3. **[MEDIUM] 行 5-8、42：负起始时间被静默钳制到 0，未保证区间单调与一致性**  
   - 现状：例如 `start=-1,end=2` 不触发等分，最终输出 `00:00:00,000 --> 00:00:02,000`。  
   - 风险：输入异常被悄悄“修饰”，可能制造重叠/倒序而非显式修复或报错。

4. **[MEDIUM] 行 8：超大时长转换存在饱和语义，缺少上界检查**  
   - 现状：`(seconds * 1000.0).round() as u64` 对超大值会饱和到 `u64::MAX`（或在乘法后 `inf` 仍饱和），输出极端时间。  
   - 风险：异常输入时产生不可用时间戳（如百万年量级），且无错误信号。

5. **[MEDIUM] 行 40-44：SRT 行分隔固定 `\n`，未输出 CRLF**  
   - 现状：仅使用 LF。  
   - 风险：多数播放器可兼容，但部分 Windows/老旧工具链按 CRLF 解析更稳，存在兼容性风险。

6. **[LOW] 行 43：`text.trim()` 会删除用户有意保留的前后空白/空行**  
   - 现状：字幕内容被“清洗”。  
   - 风险：歌词/排版型字幕（前导空格、结尾空格、空白行）语义丢失。

7. **[LOW] 行 38-45：字符串构建未预分配容量，且多次 `format!` 产生额外分配**  
   - 现状：大批量片段时分配次数偏多。  
   - 风险：性能次优（非功能性问题）。

## 2) 详细分析与修复建议

### 问题1（HIGH）：全量覆写时间戳
- **原因**：把“存在异常片段”与“全部片段都应重建时间”绑定。  
- **建议**：
  1) 先逐段校验（`is_finite && start>=0 && end>start`）；
  2) 仅对坏片段做修复（局部插值/兜底固定时长）；
  3) 只有在“全部无有效时间戳”时才走全量等分。

### 问题2（HIGH）：`NaN/Inf` 静默流入格式化
- **原因**：`NaN` 与比较操作不成立，绕过 `needs_distribute`。  
- **建议**：
  - 增加统一校验函数：`valid_ts(start,end) = start.is_finite() && end.is_finite() && start>=0.0 && end>start`；
  - 若任一无效，进入明确修复分支并记录日志/返回错误（取决于产品策略）。

### 问题3（MEDIUM）：负值与单调性
- **原因**：`format_ts` 做显示层钳制，但业务层未保证时间轴合法。  
- **建议**：
  - 在 `build_srt` 内先归一化：
    - `start=max(start,0)`；
    - `end=max(end,start+min_delta)`；
    - 确保与前一段 `prev_end` 单调不倒退。

### 问题4（MEDIUM）：极值上界缺失
- **原因**：float->int 饱和语义掩盖异常。  
- **建议**：
  - 在 `format_ts` 前做上界约束（例如 `MAX_SRT_SECONDS`）；
  - 超界时返回错误或钳制到业务可接受最大值并告警。

### 问题5（MEDIUM）：LF/CRLF 兼容性
- **原因**：SRT 常见实现偏向 CRLF。  
- **建议**：
  - 统一使用 `\r\n` 写出；或提供可配置换行策略。

### 问题6（LOW）：`trim()` 改写文本
- **原因**：对显示文本做了不可逆裁剪。  
- **建议**：
  - 改为 `trim_end_matches(['\r','\n'])`（仅去尾部换行），或完全保留原文。

### 问题7（LOW）：构建性能
- **原因**：`String::new + format!` 高频分配。  
- **建议**：
  - `String::with_capacity(segments.len() * 64 + text_total_len_estimate)`；
  - 使用 `push_str`/`write!` 复用缓冲区。

## 3) panic路径与安全评估

- **显式 panic 路径**：未发现可稳定触发的显式 panic（除 OOM 这类运行时不可恢复情况）。
- **索引越界**：未发现。
- **时间戳溢出**：无 Rust 整数溢出 panic，但存在“饱和导致逻辑错误”的风险（见问题4）。
- **安全漏洞**：未见直接注入/RCE 类漏洞；主要是数据正确性与鲁棒性问题。

---

## 4) 整体代码质量评估

- **优点**：实现简洁、可读性好；空输入可安全返回空串；已有 UTF-8/BOM 相关单测。  
- **主要短板**：异常时间戳处理策略过于粗糙（全量覆写、静默钳制），边界值与兼容性策略不够严格。  
- **结论**：**可用但鲁棒性不足**。建议优先修复 HIGH 问题（1/2），随后完善单调性与极值处理（3/4），再处理兼容性与性能优化（5/7）。
